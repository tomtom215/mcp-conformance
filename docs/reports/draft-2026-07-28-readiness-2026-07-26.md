# Draft `2026-07-28` readiness — measured, two days before the text

**Measured:** 2026-07-26 · **Suite:** `@modelcontextprotocol/conformance@0.2.0-alpha.9`
· **Spec revision requested:** `2026-07-28` · **SUT:** `mcp-everything-server` at
workspace HEAD (rmcp 1.7.0, `2025-11-25`)

**Result: 1 passing, 20 failing, 1 informational across 20 scenarios.**
Reproduce with `cargo xtask draft-readiness`; the figure is committed as
[`conformance/draft-readiness.json`](../../conformance/draft-readiness.json) and
ratcheted in CI.

---

## Why measure a score we expect to be bad

The `2026-07-28` change inventory ([register 1.5a–1.5f](../plan/01-ecosystem-context.md))
is a list of *what* changes. A list cannot say how large the migration is, in
what order it has to be done, or whether progress on it is real. Before the
final text ships, the one thing that can be established empirically is the
**starting line** — and a starting line is only useful if it cannot drift.

So this is not a conformance claim about `2026-07-28`. The requirement registry
does not describe that revision yet, and the validator is deliberately not
involved: replaying these sessions through a `2025-11-25` registry would produce
a verdict about the wrong specification. This is the official runner's draft
scenarios against today's server, and nothing more.

## What the number actually says

Every failure is the **same failure**. The draft runner opens with an ordinary
request — SEP-2575 removes the `initialize`/`initialized` handshake, so
`tools/list` arrives first, carrying its protocol version in `_meta` — and rmcp
1.7.0's streamable-HTTP server rejects it before any handler runs:

```text
Error: Failed: HTTP 422: expected a JSON-RPC result for 'tools/list',
       got non-JSON body (content-type (none))
```

Twenty scenarios, one cause, at the transport/lifecycle seam. Nothing about
tools, prompts, resources, or completion is being measured here at all: those
scenarios never reach the capability they are named for. The session tap
recorded nothing, because no session was ever admitted.

That is worth knowing precisely because it is *narrow*. The migration is not
twenty independent pieces of work; it is one — the stateless lifecycle — and
everything else is unmeasurable until that lands. It confirms the roadmap's
existing sequencing (M2.5 line 2's registry content and the
`context::draft` state machine first) rather than revising it.

## The one thing that passes

`dns-rebinding-protection / localhost-host-rebinding-rejected` — **SUCCESS**.

The `Host`/`Origin` policy that closes the CVE-2026-42559 class
([05-security-model.md](../plan/05-security-model.md)) is enforced in middleware
ahead of any protocol handling, so it is revision-independent: the evil-host
probe is rejected with 403 whichever lifecycle the client speaks. The
scenario's *other* check (`localhost-host-valid-accepted`) fails for the same
422 reason as everything else — the legitimate probe is admitted by the policy
and then rejected by the lifecycle.

A security property that survives a protocol rework unchanged is the strongest
argument available for enforcing it at the transport boundary rather than inside
the protocol handler.

## Reading the informational row

`server-sse-multiple-streams / server-sse-streams-functional` reports **INFO**
("Server returned JSON for all requests — SSE streaming is optional"), not a
failure. The baseline records statuses verbatim rather than folding them into a
passed/total ratio, for the same reason the registry reports capability-gated
requirements as *not-applicable* instead of passing them: a denominator that
silently absorbs "not applicable" is how a conformance number becomes a lie.

## What this predicts for M2.5

- The migration's critical path is the **lifecycle at the transport seam**, not
  the capability surface. Until a request without a handshake is accepted, no
  other draft conformance work can be validated end to end.
- rmcp's `3.0.0-beta` line already implements that lifecycle
  ([register 3.1](../plan/01-ecosystem-context.md)), which makes the SDK-upgrade
  decision and the revision migration one piece of work rather than two.
- When the final text ships, this number becomes the migration's progress meter:
  it can only move deliberately, in the commit that earns it.

## Method

```console
$ cargo xtask draft-readiness           # measure and compare to the baseline
$ BLESS=1 cargo xtask draft-readiness   # re-record after a deliberate change
```

The task builds the server with every feature, serves it on an OS-assigned
loopback port, runs the pinned draft suite against it, and reads each
scenario's `checks.json`. Both pins are exact — a ratchet whose input floats is
not a ratchet — so a suite bump is a deliberate commit that re-measures,
re-blesses, and updates [register 2.4](../plan/01-ecosystem-context.md)
together. The scheduled `draft-readiness` CI job runs it weekly.
