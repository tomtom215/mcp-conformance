# The cross-SDK matrix

Each Tier 1 SDK the matrix covers — TypeScript, Python, Go and Rust — ships a
conformance server: the server its maintainers run the official suite against.
This page records each of those servers, at each revision it serves, while an
official SDK client drives it, and judges every recording with this project's
validator. Nothing of this project's speaks MCP in these sessions; the recorder
and the judge are the only parts of it involved.

The table below is generated by `cargo xtask sdk-matrix` from the golden
reports committed under [`corpus/`](corpus.md), and `cargo xtask gates` fails
when it drifts from them. A scheduled job re-records every session with the
pinned SDKs each week and fails if the results differ from the committed ones,
so a row here is what the pinned release does today rather than what it did
once. How each session is recorded, with the exact commands, is
[Recording an SDK's server](sdk-servers.md).

## Reading a row

Each row is one recorded session. *Verdict* and the four counts are the
report's, with the same meaning as in [Reading a report](reading-a-report.md):
**not observed** counts the clauses the session carried nothing to judge, so a
short session is not mistaken for a conforming one. *Wire schema* is every
message checked against the revision's published JSON Schema. **Not served**
means the server does not implement that revision — the client asked, and the
server answered with an older one — so there is no session to judge.

Every server at a revision is driven by the same client running the same
script, so the difference between two rows of one revision is the server's.
The script is small — list, call, read, get — so these sessions evidence the
common surface. Compare like with like: a row with more passes did not
necessarily conform better; it may only have been asked more.

## Findings are reported, not hidden

A failing row is a finding against that SDK's pinned release, stated with the
clause it breaks and a link to the report and the recording it came from. Each
was read against the recording before being published — a check can only be as
honest as the capture it reads, and the corpus's own history has findings that
turned out to be the tool's, not the implementation's
([the trace corpus](corpus.md)). A finding you believe is wrong is a bug to
file with its requirement ID; the
[dispute process](https://github.com/tomtom215/mcp-conformance/blob/main/CONTRIBUTING.md#reporting-verdict-disputes)
says how each is triaged.
