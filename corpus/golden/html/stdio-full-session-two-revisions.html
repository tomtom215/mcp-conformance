  • BASE-041MUSTThe umbrella clause the BASE area mechanizes requirement-by-requirement; it has no observable beyond its constituents. Same role as BASE-012 at 2025-11-25, widened by this revision from 'base protocol and lifecycle management' to 'base protocol, versioning, and the message patterns'.

  • BASE-050MUSTWhat a client 'considers invalid' is internal judgment. The observable consequence — a client refusing to proceed — is client conduct after receipt, outside a server-side trace, and indistinguishable from any other reason it stopped.
  • BASE-051MUSTThe backward-compatibility rule binds the client's *interpretation* of an absent field, which leaves no wire artifact: the trace records that `resultType` was absent, not that the client read it as `complete`.
  • BASE-055MUST NOTBinds allocation — assigning a new meaning to a code in -32000..-32019 — which is an act of whoever defines codes, not a message. A code observed on the wire carries no record of when or by whom it was allocated, so a legacy code in use is indistinguishable from a newly allocated one. Its use is the sentence's other half, BASE-083, which is a SHOULD NOT and is checked at that level: until 2026-10-04 this entry carried both halves at MUST NOT and reported every use of -32000 as a MUST failure.
  • BASE-056MUST NOTWhat a receiver assumes about a legacy code's meaning is internal; only conduct following from the assumption could surface, and attributing it requires the assumption. Same boundary as BASE-025 for reserved `_meta` keys.

  • BASE-063MUST NOTReliance is internal reasoning; its only wire form is a difference: a request refused on a connection that has carried no `server/discover` and the same request served after one. A recording cannot attribute that difference. The half a single exchange does show is judged elsewhere: every request must carry its own context (BASE-030), and a request that omits it must be rejected rather than served from context an earlier request established (BASE-031).
